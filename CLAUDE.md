# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Super Dario is a 2D platformer written in Go with [Ebitengine](https://ebitengine.org). It is a parody/fan game (see the disclaimer at the top of [README.md](README.md)) — four fictional "Claude" characters rescued from a "Distillation Syndicate." Every sprite, tile, backdrop, sound effect, and music track is generated by code at startup; there are **no asset files** apart from the generated icon bundles. This ships as a single self-contained binary per platform, and as a single self-contained HTML file via Go's js/wasm target.

## Commands

```bash
go run ./cmd/superdario         # run the game
go test ./...                   # run all tests
go vet ./...                    # vet
gofmt -l -w .                   # format
make check                      # fmt + vet + test
make web                        # single-file browser build -> dist/web/SuperDario.html
```

Run a single test:

```bash
go test ./internal/world -run TestName
```

Tests import Ebitengine transitively, which opens a display via `init()`. On a headless Linux box (e.g. CI) this needs `xvfb-run -a go test ./...`; on Windows/macOS dev machines with a real display it just works.

### Build

```powershell
.\build.ps1                      # test + build dist\windows-amd64\SuperDario.exe (pure Go, no cgo)
```

```bash
./build.sh darwin                # arm64 only; must be built on a Mac (cgo)
./build.sh linux                 # needs libgl1-mesa-dev xorg-dev libasound2-dev (cgo)
./build.sh web                   # js/wasm, pure Go; no cgo or platform headers
```

`make windows|linux|darwin|web` are the equivalent Makefile targets. Windows links with `-H=windowsgui` (no console flash); `-version` and `-save-path` still work from a terminal by borrowing the parent console.

`cmd/buildweb` builds the wasm binary, gzips it, and inlines it plus Go's `wasm_exec.js` into `web/index.html`. The HTML is generated into `dist/` (ignored, like the other build outputs); the loader source is committed. The browser build has no command-line flags and stores saves in localStorage — see [Saves](#saves-internalsave) below.

### Icons

The icon is drawn in code (`internal/gfx/icon.go`). After changing it, regenerate the committed bundles:

```bash
go run ./cmd/genicon .
```

This writes `assets/icon.ico`, `assets/icon.icns`, `assets/icon_*.png`, and `cmd/superdario/resource_windows_*.syso`. Generation is deterministic. CI regenerates and diffs these and fails the build if they've drifted from the source — always run this after touching `icon.go` and commit the result.

### Dev tools (`cmd/`)

- `cmd/superdario` — the game itself
- `cmd/buildweb` — builds the single-file js/wasm HTML build (see above)
- `cmd/genicon` — regenerates icon bundles (see above)
- `cmd/artdump` — dumps generated sprite sheets to PNG for visual review
- `cmd/shots` — drives the game headlessly through its screens/scenes and captures PNGs, used to review scene appearance without playing by hand

## Architecture

Six packages, layered bottom-up:

```
internal/core   screen size, tile size, physics constants (no dependencies)
internal/gfx    palette, ASCII-art sprite decoder, bitmap font, procedural
                tilesets, parallax backdrops, particles, bosses, icon, gamepad diagram
internal/sfx    chiptune synth, tracker sequencer, soundtrack, SFX
internal/save   save slots, settings, key/pad bindings, atomic JSON persistence
                (native) / localStorage (web)
internal/world  tiles, chunk-assembled levels, physics, enemies, bosses — the
                actual platforming simulation, independent of scenes/menus
internal/game   Ebitengine scene stack, input bindings, HUD, menus, cutscenes —
                wraps a world.World for the play scene
```

`internal/world` has no knowledge of `internal/game`; it is a self-contained simulation driven by a `world.Input` struct each tick and exposing a `Status` (`StatusPlaying` / `Dying` / `Dead` / `Cleared` / `TimeUp`) that the owning scene polls. This split is what lets `cmd/shots` and the autopilot-driven tests puppet the game without a real display/input loop.

### Scene stack (`internal/game`)

`Game` (in `game.go`) is the Ebitengine entry point. It holds a single active `Scene` plus a `pending` one, and cross-fades between them (`fadeDir`/`fade` in `Update`). Each `Scene` implements `Enter`/`Update`/`Draw`. Scenes: `TitleScene`, map/level-select (`scene_map.go`), `scene_play.go` (wraps a `world.World`), `scene_controls.go` (rebinding UI, keyboard + gamepad tabs), `scene_files.go` (save slots), `scene_story.go` (cutscenes), `scene_misc.go` (pause, game over, etc.).

`RunState` on `Game` carries progress between levels within one session (world/level index, lives, score, tokens, power state, which characters are rescued). `Game.Autopilot`, when set, supplies `world.Input` instead of reading the controller — this is what `cmd/shots` and the stage-traversal tests use.

### Levels (`internal/world/chunks.go`)

Stages are hand-authored ASCII chunks, bottom-aligned against the floor, assembled at load time:

```
"...==B==?==.....",
"......o.o.......",
"....g.......g...",
"################",
```

### Art (`internal/gfx`)

Characters/enemies are ASCII art, one character per pixel indexing a shared palette (`internal/gfx/palette.go`):

```go
"..bbbdddddbbb...",
"..bb13011301d...",   // 'b' hair, 'd' skin, '1' glasses frame, '3' lens, '0' pupil
```

Palette substitution is used for recolors (e.g. Dario's "Aligned" form reuses the Small/Scaled frames through a 3-entry substitution rather than storing separate art). Tiles, backdrops, bosses, the app icon, and the gamepad diagram are drawn from primitives instead of ASCII grids — see the five `Theme` structs for the per-world tilesets.

### Music (`internal/sfx`)

A small tracker: each lane is a list of bars, each bar exactly sixteen sixteenth-note tokens:

```go
"e5 - - . g5 - - . c6 - - - b5 - - -",   // '-' holds, '.' rests
```

Lanes loop independently at their own length (a 1-bar drum pattern under an 8-bar melody). Rendered sample-by-sample on the audio thread via pulse/triangle/saw/noise oscillators with ADSR envelopes, stereo delay, and a soft clipper.

### Saves (`internal/save`)

Three slots, written after every stage, level select, and quit-to-map. Atomic (temp file + rename); unreadable JSON is moved to `save.json.corrupt` instead of being overwritten. Control bindings are stored by name so they survive engine updates that renumber key constants.

The web build swaps the file layer for localStorage (build-tagged `storage_file.go` / `storage_web.go`); the JSON document and public API are identical. The key is `superdario:SuperDario/save.json`, and the Options screen displays it. A browser with storage disabled must still be able to boot: the JS storage calls are wrapped in try/catch and failures surface as the usual on-screen save toast, so keep that path error-tolerant.

## Test suite intent

The tests mostly guard against content mistakes that are invisible until you actually play into them (see [README.md](README.md#tests) for the full list) — e.g. every chunk is rectangular and pairs pipe halves, no stage has a step-up taller than a running jump can clear, an autopilot holds right through every stage for a simulated minute and must never end up inside a solid tile, every boss reaches a stompable state within 30s, and saves round-trip with forward-only unlock progression. When changing level chunks, boss behavior, physics constants in `internal/core`, or music/SFX, run the full suite — these are exactly the kind of regressions it's designed to catch.
